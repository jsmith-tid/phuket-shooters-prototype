# Phuket Shooters gap audit

**Audit date:** 21 October 2026. **Baseline:** local `main` at `fdf3b9be6bb95cd01d14da8a150723361e6a5d51` (Node 24.13.0, Windows/PowerShell). **Scope:** audit only; no site fixes, deployment, DNS, emails or real submissions.

**Post-audit update (22 October 2026):** the Tour Operators page now uses the owner-supplied exterior/parking photo `587_0.jpg` in all three languages. GAP-11's café-image observation is resolved by this later change; coach approach/turning instructions remain unconfirmed under TO-04. The findings below otherwise describe the original audit baseline.

## Readiness and next actions

The static prototype is coherent enough for stakeholder walkthroughs: 56 routes build, local links and noindex checks pass, all five core languages exist, and the English/Thai/Chinese group flow remains separate and visibly a demo on its form page. It is **not ready to accept real requests or replace Wix**. The most material prototype gaps are incomplete enquiry previews, weak individual-form date/time handling, and a no-JavaScript fallback that can put individual-form values in the URL. The operator information page also describes a future live booking process more assertively than the current demo allows.

The three most useful next actions are: (1) make the two dummy enquiry journeys safe and reviewable, including the no-JavaScript case; (2) decide what an individual customer should select and what prices include, then connect choices to the enquiry; (3) agree the production hostname, confirmed Wix expiry/billing dates and request-handling owner before scheduling the 23–27 November migration window.

**Interpretation:** P1 breaks or misleads a core journey; P2 materially improves understanding/usability; P3 is polish. Production dependencies have a separate deadline sequence below. Missing backend, payment, CMS and real confirmations are *not* prototype defects under the current decisions.

## Baseline, method and limits

- Read `README.md`, `package.json`, `CONTENT_REVIEW.md`, `docs/launch-checks.md`, build/check scripts, content modules, CSS/JS, assets, workflow and the earlier operator brief. No applicable `AGENTS.md` was found in the repository.
- Ran `npm run build` followed by `npm run check`: **56 pages built; checks passed** for noindex, `lang`, generated local `href`/`src`, disabled homepage strip, three-language operator routes/links and demo-only group button. An initial check was accidentally parallel with the build and hit a missing file; the sequential rerun passed and is the valid result.
- Used the existing local server at `http://localhost:8080` and headless Chromium device emulation at 360/390, 768 and 1440 CSS px to inspect representative routes and execute selected interactions. Did not alter the user's running server. Sampled English home/prices/book/operator information/group request; Thai and Chinese operator routes; Arabic home; Russian booking. Chromium is **not** iOS Safari/Brave or a fluent translation review.
- Both published domains were inaccessible to the available web and network tools. Thus deployed behaviour, current Wix facts, external `tel:`, WhatsApp, email, Google Maps/reviews and social destinations could not be independently verified. No real messages, calls or requests were made. Local results are not a live performance score.
- The pre-existing untracked `.vscode/`, audit brief and `public/assets/images/PS-main-tours-English-mob.jpeg` were left untouched. The latter was copied into local `dist/` by the build but is not referenced by the page source; this audit is of the current source plus the generated local build, not proof of remote deployment.

### Interaction, access and technical observations

The sampled 390px home, prices, book, operator and Arabic home, 768px and 1440px home had no document-level horizontal overflow in Chromium. At 360px the individual form's eight text/date/time/textarea controls shared the same left/right edges inside the card, and the ID note appeared below fields. This **does not close the previously reported iOS Safari/Brave date/time-width issue**; real-device testing remains necessary. Mobile screenshots showed the group form below its introductory/contact block, so reaching it requires scrolling; that is a prioritisation opportunity, not a demonstrated break. Arabic sampled with `lang="ar"`, `dir="rtl"` and RTL computed direction. Keyboard focus styles, skip link, reduced-motion CSS, explicit `lang` and local social icons exist in source. Escape-to-close is absent for menus; no full keyboard/screen-reader, 200% zoom, contrast or native-device audit was possible.

Generated pages retain `<meta name="robots" content="noindex, nofollow, noarchive">` and `public/robots.txt` disallows all. There is no analytics vendor, storage API or fetch call in the site JavaScript; event hooks dispatch a local `phuketshooters:event`. One individual `booking_submit` action fires twice (click hook plus submit handler). Group preview runs locally; it issues no real booking. The local-link checker does not inspect runtime navigation, field validation, external destinations, console/network failures, image rendering or translations; the Pages workflow builds but does not run `npm run check`.

## Separate production dependencies and migration sequence

These are **future launch work**, not missing prototype features. Neither a staff CMS nor accounts, checkout, automatic capacity, partner portal or custom dashboard is assumed necessary. Wix is hosting only; do **not** migrate domain registration or email/workspace by assumption.

| Deadline impact / sequence | Dependency and completion test |
| --- | --- |
| **Immediate decision, high** | Confirm production hostname and Wix billing/expiry, who controls domain/DNS, and who owns requests. If keeping the no-hyphen Wix domain, point that hostname at the new host and redirect old Wix paths as appropriate; if adopting the hyphenated prototype hostname, plan domain-level 301s, canonical/hreflang changes and search transition deliberately. Preserve existing MX/SPF/DKIM/DMARC and other email DNS records. |
| **Before build freeze, high** | Define real individual/group request delivery, server-side validation, spam controls, safe retries/monitoring, verified sender/recipient if transactional email is chosen, staff inbox ownership, manual confirmation and a shared record of confirmed bookings/changes. Resend (if selected) supplies email transport, not the whole submission backend. Cash on day or card arranged by telephone are the only confirmed payment methods; collect no card details. |
| **Before content freeze, high** | Owner-approved facts and legal/safety wording, fluent translations, current staff/image consent, real news or removal of the Action Air example, and removal of preview-only notices *only after* a real flow exists. Decide privacy/retention/access wording for future form data and third-party Maps/analytics. Export/preserve any Wix content or records still needed. |
| **Before migration, high** | Inventory actual Wix URLs, define relevant redirects, final canonical origin, sitemap, hreflang, robots/indexing policy, structured data only after factual approval, production headers/secrets and deploy/rollback procedure. Confirm contact links and Maps pin on final host. |
| **After functional release, medium** | Configure privacy-appropriate analytics and meaningful, non-duplicated conversion events without form-value payloads; monitor form delivery, redirects, indexing/search and mobile errors. |

**Suggested calendar:** by early November settle hostname, dates and request ownership; mid-November implement/test real delivery, content and redirect plan; target 23–27 November for a controlled migration and smoke test; retain buffer before the *approximate* 5 December Wix deadline. The deadline is unverified—do not allow billing to lapse until replacement and rollback are proven. A real production launch also needs agreed support/rollback ownership and monitoring after cutover.
